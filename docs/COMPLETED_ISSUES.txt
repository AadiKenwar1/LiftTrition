*1. Deleting your account can strand you half-signed-in
   The app erases the account on the server FIRST, then tries to upload
   any unsaved changes. Those uploads can never succeed for an account
   that no longer exists, so the 60s wait always fails, local cleanup
   never runs, and the user stays "signed in" to a dead account. Only a
   reinstall escapes.
   Where: context/AuthContext/functions/accountFunctions.tsx
   Fix: upload (or discard) pending changes BEFORE deleting the server
   account; always clear local state once the server confirms.

   PLAN
   Root cause: local cleanup hangs off a Gate C flush that can never
   drain once the server account is gone — and the flush itself is
   the wrong requirement. The user has already confirmed "all your
   data will be permanently deleted"; unsynced changes are a subset
   of that, and uploading them seconds before the server erases them
   protects nothing. Deletion needs no flush at all.
   Steps:
   1) Keep the current macro-order — edge function first. If that
      call fails, abort: account and local data both intact, and
      profile.tsx's existing generic error alert is the right
      outcome. Never wipe local state before the server confirms.
   2) Once the edge function confirms, deleteAccount() stops calling
      signOut() and instead runs clearLocalSession() (F4)
      unconditionally — no flush, each teardown step guarded;
      disconnectAndClearPowerSync() is what actually discards the
      now-meaningless upload queue — then clearUserStorage(userID)
      (issue 19). signOut keeps Gate C for the normal sign-out
      path, where unsynced data still matters.
   Files: accountFunctions.tsx.
   Verify: log a meal in airplane mode → Delete Account → clean
   abort, account intact, data still there. Online with unsynced
   changes: delete → no 60s flush wait → lands on login, relaunch
   stays signed out, no orphan local data.

*2. Anyone who ever contacted support can never delete their account
   The server delete function forgets the support_requests table. The
   database refuses to remove a user who still has rows there, so
   deletion fails forever. Worse, the six deletes that ran first are not
   error-checked, so the user's data is wiped even though the account
   survives.
   Where: lib/supabase/functions/deleteAccount/index.ts
   Fix: also delete support_requests, check every delete's error, do it
   all in one transaction.

   PLAN
   Root cause: deletion is a hand-maintained list of table deletes in
   application code. Any new user-owned table (support_requests today,
   whatever comes next tomorrow) silently breaks it, and per-table
   error checking is busywork that was (predictably) skipped.
   Steps:
   1) Push ownership into the schema: migration that re-declares every
      top-level user_id foreign key as ON DELETE CASCADE — workouts,
      user_exercises, nutrition_entries, saved_nutrition_entries,
      weight_progress, settings, support_requests. (Child tables
      already cascade from their parents.) Version it as
      lib/supabase/migrations/user_cascade.sql.
   2) Shrink the edge function to: authenticate →
      auth.admin.deleteUser(userId) → check the ONE error → respond.
      Postgres deletes all user rows atomically in the same
      transaction as the auth user — nothing partial, nothing to
      forget, no per-table error handling to maintain.
   3) Rule going forward (one line in the migration header): any new
      table referencing auth.users must declare ON DELETE CASCADE —
      deletion coverage is then automatic forever.
   Files: new migration, lib/supabase/functions/deleteAccount/index.ts.
   Verify: seed a user with data in every table incl. a support
   request → delete → auth user and all rows gone in one shot; make
   deleteUser fail → nothing was deleted (atomicity).

*3. One decimal calorie value can jam syncing forever
   The database column for calories only accepts whole numbers, but the
   food-search and manual-entry screens save unrounded values (a
   FatSecret item like 130.5 cal x 3 servings is enough). The phone
   accepts it, the server rejects it, and sync retries the same bad row
   forever - nothing after it ever uploads. The only way out shown to
   the user (force sign-out) throws away all their unsynced data.
   Where: foodDBModal.tsx / addNutritionModal.tsx -> Connector.ts
   Fix: round + sanity-check numbers once at the save boundary
   (nutritionEntryToRow), or make the column accept decimals.

   PLAN
   Root cause: two holes, both structural. (a) The persistence
   boundary trusts every screen — rows reach SQLite (then Postgres)
   with whatever the screen produced (fractional calories from
   foodDB/editManualEntry, NaN from unvalidated parsing). (b) The
   Connector retries a permanently-rejected row forever, so one bad
   value poisons everything behind it.
   Steps:
   1) Sanitize once at the converter boundary (F1): in
      nutritionEntryToRow and savedNutritionEntryToRow (and the two
      ingredient-insert loops in the same file), pass every numeric
      field through sanitizeInt/sanitizeMacro — non-finite → 0,
      calories/macros/quantity → 1 decimal. Every
      write path (manual, foodDB, saved, photo/AI, edits) funnels
      through these two converters, so no screen — current or future
      — can produce an out-of-contract row again.
   2) Dead-letter backstop in the Connector (F3b): data/integrity
      errors from Postgres are non-retryable → report + skip +
      complete, never wedge. This also automatically un-jams any
      user already stuck when the update ships.
   3) Decision (2026-07-13): decimal calories ARE allowed — migrate
      the calories columns on nutrition_entries and
      saved_nutrition_entries from INTEGER to REAL (Postgres
      migration + AppSchema column.integer → column.real; settings
      goal columns stay INTEGER). The ingredient tables already
      store calories as REAL, so this also stops an entry total
      disagreeing with its own ingredient breakdown. Ship the
      migration before/with the app update; it alone un-jams users
      already wedged on a decimal row. Note REAL does NOT fix the
      NaN case — the boundary sanitizer (step 1) covers that.
      Display: DailyIntakeCard already rounds at render, so totals
      stay whole; entry rows may show one decimal — accepted.
   (Screen-side parsing correctness is issue 10/11/12 — this issue is
   the boundary + retry policy, which hold even if a screen slips.)
   Files: context/NutritionContext/database/powersyncStore.ts,
   lib/utils/number.ts (F1), lib/powersync/Connector.ts (F3),
   calories REAL migration, lib/powersync/AppSchema.ts.
   Verify: log a 130.5-cal FatSecret item ×3 → row stores 391.5 and
   syncs; hand-inject a NaN row into the queue → it is skipped and
   reported, queue drains, later entries upload.

*6. A bad launch can dump an existing user back into onboarding
   If loading settings fails once, the app quietly pretends the user is
   brand-new (blank defaults, onboarding not complete) instead of
   showing an error. If they re-do onboarding, their real goals and
   macros on the server get overwritten.
   Where: context/SettingsContext/index.tsx (load catch block)
   Fix: show a retry/error screen on load failure; never treat a failed
   load as a fresh account.

   PLAN
   Root cause: a failed load and a brand-new user produce the exact
   same state (defaults + loaded=true), so the route guard cannot
   tell disaster from day one. The same catch-and-pretend pattern is
   copy-pasted in Nutrition, Workout, and PowerSyncGuard.
   Steps:
   1) Introduce load status via one shared hook (F6a): each context's
      load runs through useAsyncLoad → status 'loading' | 'ready' |
      'error' + retry(). The catch block stops writing defaults —
      error is its own state, prior data stays untouched. Contexts
      expose loaded (status==='ready'), loadFailed, retryLoad.
   2) Route guard in app/_layout.tsx (StackLayout): an errored
      context never reaches 'ready', so the existing
      !allContextsLoaded branch already keeps AppLoadingScreen up
      with the Stack unmounted — pass loadFailed + retryLoad into it
      to surface the F6b retry affordance. With the Stack unmounted,
      onboarding is unreachable from an error state by construction.
   3) Persistence stays naturally safe: the persist effects key on
      loaded/hasLoadedUserData, and an errored context never reaches
      'ready' — so re-onboarding-over-real-data becomes impossible,
      not just unlikely. Give PowerSyncGuard's catch (28-31) the
      same error-state treatment.
   Files: lib/hooks/useAsyncLoad.ts (new),
   components/GuardComponents/AppLoadingScreen.tsx (error variant),
   Settings/Nutrition/Workout context index.tsx, PowerSyncGuard.tsx,
   app/_layout.tsx.
   Verify: make loadSettingsAndBw throw once → loading screen shows
   "tap to retry" (NOT onboarding); Retry succeeds → tabs with real
   data; fresh account still onboards normally.

*7. Food logged the next morning lands on yesterday
   The selected date is set once when the app starts and never rolls
   over at midnight. Use the app in the evening, leave it in the
   background, log breakfast tomorrow -> it's saved to yesterday, today
   shows 0 calories, and the streak breaks.
   Where: context/NutritionContext/index.tsx (selectedDate)
   Fix: reset the selected date to today when the app comes back to the
   foreground on a new day.

   PLAN
   Root cause: "today" is captured once at provider mount
   (useState(new Date())) and nothing in the app observes the
   calendar day changing — iOS keeps the process suspended for days.
   Steps:
   1) Build useToday() (F5): today's dateKey, recomputed on AppState
      'active' (and on a mount check), updating state only when the
      key actually changes.
   2) NutritionContext: const todayKey = useToday(); one effect —
      when todayKey changes, setSelectedDate(new Date()). A user who
      deliberately picked a past date keeps it within the same day;
      crossing midnight snaps selection to the new day, which is the
      only behavior that keeps "log breakfast" correct.
   3) Same fix, same family (audited 2026-07-13 — the full list of
      frozen-"today" consumers, not opportunistic):
      a) nutritionStreak memo (NutritionContext/index.tsx ~124) is
         keyed on [nutritionData] only — a streak is relative to
         today, so it goes stale at midnight if no data changes.
         Add todayKey to the deps: [nutritionData, todayKey].
      b) progress.tsx ~80: weekStart memo captures
         getWeekStart(new Date()) keyed only on bottomWeekOffset —
         "this week" is silently last week after a suspended
         Sun→Mon crossing. Add todayKey to the deps. Same file
         ~238: the highlightIndex new Date().getDay() goes fresh
         once the memo recomputes.
      c) nutritionScreen.tsx ~28 and logsModal.tsx ~112 compute
         isToday from getDateKey(new Date()) at render time — they
         self-heal once (a)/step 2 trigger re-renders, but switch
         them to useToday so they are correct by construction.
      (Checked and fine as-is: graphFunctions, volumeFunctions,
      bodyWeightFunctions compute today at call time inside
      per-render/per-action functions; devTest calendar components
      are dev-only.)
   Files: lib/hooks/useToday.ts (new), NutritionContext/index.tsx,
   app/(tabs)/progress.tsx, app/nutritionScreens/nutritionScreen.tsx,
   app/workoutScreens/logsModal.tsx.
   Verify: evening session → background the app → advance the device
   day → foreground: date chip says "Today", breakfast lands on the
   new day, streak recomputes; cross a week boundary → "this week"
   bar chart shows the new week with today highlighted.

*10. Typing "80,5" (or a stray ".") corrupts weight and macro goals
    Number parsing lets NaN through every check in the body-weight modal
    and manual meal entry. On iPhones set to a comma-decimal region
    (most of Europe), the keypad only offers a comma - so their FIRST
    decimal weight entry corrupts body weight, all four macro targets,
    and the chart. Meals get NaN calories the same way.
    Where: updateBWModal.tsx, addNutritionModal.tsx + both validators
    Fix: one shared number parser (comma->dot, reject non-finite) used
    by every numeric field.

    PLAN
    Root cause: the app has three parsing policies for one input
    class (strict Number.isFinite in logsModal, parseFloat||0 in
    editManualEntry, raw Number/parseFloat in updateBW/addNutrition)
    and none normalizes the decimal comma iOS keypads produce.
    Steps:
    1) Build F1's parseNumericInput and make it the only reader of
       numeric TextInputs: updateBWModal (null → block submit),
       addNutritionModal and editManualEntry (empty → 0 for optional
       macro fields; non-null required for a typed value),
       logsModal (already strict — switch it too so comma locales
       can log sets), plus the quantity fields (issue 11) and the
       photo editor (issue 12).
    2) Belt-and-suspenders in both validators: validateHeightWeight
       and validateNutritionEntry reject non-finite values first —
       so even a future screen that skips the parser can't push NaN
       through.
    3) Disable submit CTAs while a required field parses to null, so
       the failure is visible at the field, not after save. (The
       persistence boundary from issue 3 remains the last line of
       defense.)
    Files: lib/utils/number.ts (F1), updateBWModal.tsx,
    addNutritionModal.tsx, editManualEntry.tsx, logsModal.tsx,
    SettingsContext/functions/validator.tsx,
    NutritionContext/functions/validator.tsx.
    Verify: on a comma-locale simulator type "80,5" → weight 80.5
    everywhere (chart included); "12..5" / "." is rejected with a
    message and cannot corrupt macros; meals can't save NaN.

    Files: foodDBModal.tsx, savedNutritionModal.tsx.
    Verify: log 0.5 servings from food search → half the macros are

12. The photo-meal editor can't take decimals at all
    Each keystroke is parsed immediately, so typing "2.5" becomes "25"
    (the dot is eaten) and fields can't be cleared. Also, an ingredient
    set to 0 servings shows 0 in its own row but still counts as 1 in
    the totals that get saved.
    Where: app/nutritionScreens/editPhotoEntry.tsx
    Fix: keep the text as a string while editing, parse on save; unify
    the 0-quantity rule.

    PLAN
    Root cause: numeric state is stored as numbers and re-parsed on
    every keystroke — the field renders parse(text) instead of the
    text, so transient states ("2.", "") are destroyed as typed.
    Separately, quantity-0 means two different things because
    calcTotals treats 0 as "missing" (|| 1) while the row grid uses
    the raw value.
    Steps:
    1) Draft-string editing (the pattern every other modal already
       uses): hold each ingredient's fields as strings in state;
       TextInputs read/write the strings untouched. Parse once with
       parseNumericInput (F1) — live totals use a tolerant parse
       (null → 0), handleSave builds the numeric Ingredient list.
    2) The +/- steppers parse the current string, step, clamp at 0,
       and write back the stringified result.
    3) One quantity rule, decided in ONE place: in the shared
       sumIngredients (issue 9), use quantity ?? 1 instead of
       quantity || 1 — a missing quantity still defaults to 1, but
       an explicit 0 counts as 0. Row grid, totals card, and the
       saved entry now all agree that 0 servings = excluded.
    Files: editPhotoEntry.tsx, ingredients.ts (shared sum from
    issue 9).
    Verify: type "2.5" → field shows 2.5 and totals use it; a field
    can be cleared while editing; a 0-quantity ingredient shows 0 in
    its row AND contributes 0 to the totals that get saved.

17. Failed saves look like successes
    Every write updates the screen first and quietly logs any database
    failure - the modal closes, the checkmark plays, and the data
    vanishes on next launch. The settings row does retry, but in a tight
    loop with no backoff.
    Where: all context handlers (catch -> console.warn pattern)
    Fix: tell the user + retry, or roll the UI back; add backoff.

    PLAN
    Root cause: optimistic UI with the failure swallowed — every
    handler's catch is console.warn, so React state (what the user
    sees) and SQLite (what survives restart) silently diverge. The
    per-handler pattern makes fixing it screen-by-screen a treadmill;
    the failure policy needs one owner.
    Steps:
    1) One failure policy (F6c): reportPersistFailure(scope, error,
       { reload }) — Sentry capture, a throttled "Couldn't save your
       change" alert (throttled so a burst of failures isn't an
       alert storm), and rollback-by-reload: re-run the owning
       context's existing load so the UI snaps back to disk truth.
       One universal rollback instead of hand-written inverse
       operations per handler.
    2) Replace every catch → console.warn in Nutrition, Workout and
       Settings write handlers with that helper (each callsite is a
       one-line change).
    3) Settings retry loop: exponential backoff (1s·2^n, capped 30s)
       before bumping persistRetryNonce, and surface the failure
       alert after ~3 consecutive misses instead of spinning
       silently forever.
    4) Onboarding exception (settings.onboardingComplete === false):
       during onboarding, disk is NOT the source of truth — the
       user's answers accumulate in memory across ~6 screens and are
       only written to disk piecemeal. So reporting a settings
       failure here must NOT reload/rollback (that would wipe every
       answer since the last successful save and bounce them back
       screens). Branch on onboardingComplete: onboarding → silent
       retry-with-backoff, keep the in-memory value; normal use →
       reload+alert as above.
    5) Gate the final onboarding commit: paywall.tsx today does
       setSettings({ onboardingComplete: true }) then immediately
       router.replace('/(tabs)') — a fire-and-forget write. If that
       save fails silently, disk stays onboardingComplete=false and
       the route guard drops the user back into onboarding on next
       launch. Await this one write and gate navigation on its
       success; on failure, tell the user + retry instead of
       navigating.
    Files: lib/powersync/persistErrors.ts (new), NutritionContext/
    index.tsx, WorkoutContext/index.tsx, SettingsContext/index.tsx,
    app/onboardingScreens/paywall.tsx.
    Verify: force upsertNutritionEntry to throw → user is told, the
    entry disappears from the list (matches disk), Sentry gets the
    event; settings failure retries with growing gaps, not a tight
    loop; force a save to fail mid-onboarding → progress is kept (no
    reload/rollback); force the paywall commit to fail → user is not
    navigated into the app and is told, and a successful retry both
    persists onboardingComplete and advances to (tabs).
    Dev tooling: add lib/devtools/forceSaveFailure.ts (write analog
    of forceLoadFailure.ts — arm a scope so its next write throws,
    consumed in persistErrors/upserts) plus a SaveFailureTest Dev Hub
    page so the alert (normal vs high-severity wording), throttle,
    and onboarding-vs-normal rollback behavior are exercisable
    on-device.

19. Signing out erases the dark/light theme choice (and more)
    Sign-out calls AsyncStorage.clear(), which nukes EVERY key on the
    device — the theme preference (a device setting, not account data)
    and every signed-in user's "last exercise", not just the departing
    user's.
    Where: accountFunctions.tsx (AsyncStorage.clear())
    Fix: keep the device theme; clear only the departing user's own
    scoped keys, on both sign-out and delete.

    PLAN
    Root cause: teardown uses "clear everything" (AsyncStorage.clear())
    as its model of what a sign-out should erase. Device storage has
    three distinct owners: the Supabase auth token, removed by
    supabase.auth.signOut() itself; colorScheme, a DEVICE preference
    that must outlive every account; and user-scoped data keyed by
    userID (today just lastExercise:{userID}). clear() erases the
    device preference — the visible theme-reset bug — and, with no
    single owner naming the user-scoped set, also wipes EVERY user's
    keys on a shared device, not just the departing one. Resolution:
    last exercise is account data, not a device setting, so it is
    cleared with the departing user's other keys on sign-out too;
    colorScheme is the only survivor of a sign-out or a delete.
    Steps:
    1) F4's clearLocalSession() owns session + PowerSync teardown and
       does NOT touch AsyncStorage (the auth token goes with
       supabase.auth.signOut() inside it). Remove the blanket
       AsyncStorage.clear() / clearStorage() from signOut, forceSignOut
       and deleteAccount.
    2) lib/utils/userStorage.ts (new) is the single registry of
       user-scoped keys: it exports the key builder(s) — today
       lastExerciseKey(userID) — and clearUserStorage(userID), which
       removes them all. colorScheme is deliberately NOT in the
       registry, so it is never touched.
    3) All three teardown paths capture the departing userID from the
       session BEFORE auth is torn down, then call
       clearUserStorage(userID): sign-out / force-sign-out clear the
       leaving user's keys, deleteAccount the gone user's. Signatures
       stay () => Promise<void>, so AuthContext and profile.tsx are
       untouched.
    4) WorkoutContext imports lastExerciseKey from the registry instead
       of inlining `lastExercise:${userID}` at its read/write sites, so
       the key it stores under and the key clearUserStorage deletes can
       never drift apart.
    Files: accountFunctions.tsx, lib/utils/userStorage.ts (new),
    context/WorkoutContext/index.tsx (imports the key builder),
    accountFunctions.test.ts (assert clearUserStorage runs and the theme
    key survives, replacing the AsyncStorage.clear assertions).
    Verify: set dark mode → sign out → relaunch → still dark (theme
    survives); sign back into the same account → Progress opens on the
    default exercise, NOT your last one; delete account → that user's

22. Birthday and onboarding date can be stored one day off
    Both are saved using UTC instead of local date (the exact pattern
    the project's own docs warn about). Finish onboarding in the evening
    in the US -> stored as tomorrow; week 1 becomes unreachable in the
    progress pager. A birthday can be permanently one day early.
    Where: context/SettingsContext/database/powersyncStore.ts (settingsToRow)
    Fix: use getDateKey() for both, parse both as local dates.

    PLAN
    Root cause: there is no single serialize/deserialize pair for
    date-only values — settingsToRow serializes with
    toISOString().slice(0,10) (UTC), while the read side mixes local
    parsing (onboarding_completed_at, hand-split) and UTC parsing
    (birth_date via new Date("YYYY-MM-DD")). With no named inverse of
    getDateKey, every callsite improvises.
    Steps:
    1) F5: add parseDateKey(key) to dateHelper — local-midnight
       inverse of getDateKey. getDateKey/parseDateKey become the
       ONLY conversions between Date and "YYYY-MM-DD" in the app.
    2) settingsToRow writes birth_date and onboarding_completed_at
       with getDateKey(); rowToSettings reads BOTH with
       parseDateKey() (this also fixes the read-side half of the
       birthday bug, where new Date(str) parses as UTC midnight).
    3) Sweep the codebase for the two banned patterns —
       toISOString().slice(0,10) and new Date("YYYY-MM-DD" strings) —
       replacing with the pair (the nutrition store's hand-split
       parse becomes parseDateKey), so the correct pattern is also
       the easiest one to find and copy.
    4) Data note for the release: values already stored under the
       UTC bug may sit one day forward; that skew is not reliably
       repairable after the fact (intent is unrecoverable), but all
       new writes and all reads are correct from this change on.
    Files: lib/utils/dateHelper.ts,
    context/SettingsContext/database/powersyncStore.ts,
    context/NutritionContext/database/powersyncStore.ts.
    Verify: complete onboarding at 9pm US-Eastern (simulated) →
    stored key equals the local date, week-1 pager reachable next
    week; birthday round-trips to the exact day entered, in any
    timezone.
