PLATES AUDIT — MAJOR ISSUES
From the 2026-07-12 multi-agent audit. Confirmed-in-code issues only
(technical detail + line numbers in AUDIT_REPORT.md). Entries are moved
to COMPLETED_ISSUES.txt as they get fixed, so issue numbers here are
non-contiguous by design (11 migrated 2026-07-14).

Each issue now carries a PLAN block: an implementation plan written
from scratch against the current code, aimed at root causes rather
than symptoms. The original one-line "Fix:" hints are kept for the
record; where they differ, the PLAN supersedes them. Several plans
build on the shared foundations below (referenced as F1-F6) — build
each foundation once and every issue in its cluster becomes a small,
readable change instead of a per-screen patch.


SHARED FOUNDATIONS (F1-F6)
--------------------------
These are the six primitives the plans share. Each one retires a
CLASS of bugs, not one instance, and gives future code exactly one
place to do the thing correctly.

F1. One numeric grammar — lib/utils/number.ts (new)
    parseNumericInput(text): number | null
      trim → convert decimal comma to dot → Number() → return the
      value only if Number.isFinite, else null. This is the ONLY way
      user-typed text becomes a number anywhere in the app.
    sanitizeInt(n) / sanitizeMacro(n)
      boundary coercers for row converters: non-finite → 0, integer
      columns rounded whole, calories/macros/quantity to 1 decimal
      (calories columns move to REAL — see issue 3 step 3).
    Retires: NaN persistence, decimal-comma lockout, parseInt
    truncation, fractional values in INTEGER columns (issues 3, 10,
    11, 12).

F2. Single-flight submit guard — lib/hooks/useSubmitOnce.ts (new)
    const [guard, submitting] = useSubmitOnce()
    guard(fn) returns a handler that ignores re-entry via a
    synchronous ref (state alone is too slow for a double-tap) and
    exposes `submitting` for disabled styling. Handlers that end by
    navigating away never reset; retryable ones reset in finally.
    Retires: the double-submit class (issues 13, 14, 20).

F3. Connector: declarative upserts + a dead-letter backstop
    (lib/powersync/Connector.ts)
    a) UNIQUE_KEYS registry: { settings: [user_id], weight_progress:
       [user_id, date], user_exercises: [user_id, name] }. One
       generic createRecord path: look up the table's keys, select
       the existing row by them, update (dropping the local id) or
       insert. Replaces the two copy-pasted branches; a future
       constrained table is a one-line registration (this makes
       CLAUDE.md gotcha 3 structural instead of tribal).
    b) Non-retryable upload errors: in uploadData, classify Postgres
       errors — data/integrity violations (SQLSTATE 22*/23*) can
       never succeed on retry, so report to Sentry, skip that op, and
       complete the transaction instead of rethrowing forever. This
       is the safety net that keeps ANY future bad row from wedging
       the queue, and it un-jams already-wedged installs on update.
    Retires: permanent sync wedges (issues 3, 18).

F4. Session teardown owned in one place —
    context/AuthContext/functions/accountFunctions.tsx
    clearLocalSession(): supabase.auth.signOut({ scope: 'local' }) →
    disconnectAndClearPowerSync(), each step guarded so a failure in
    one never strands the next (the C1 lesson). signOut, forceSignOut
    and deleteAccount all end in this one function. AsyncStorage is
    NOT cleared here (see issue 19).
    Also: give UploadFlushTimeoutError and UploadFlushNotConnectedError
    a common UploadFlushError base + isUploadFlushError() so callers
    react to the category "flush cannot complete", not one subclass.
    Serves issues 1, 16, 19.

F5. Dates: one serialize/deserialize pair + a live "today" —
    lib/utils/dateHelper.ts
    parseDateKey(key): Date — local-midnight inverse of getDateKey
    (the split-and-new Date(y, m-1, d) logic that already exists,
    copy-pasted, in two stores). getDateKey/parseDateKey become the
    only date-string conversions in the app.
    useToday() (lib/hooks/useToday.ts, new): returns today's dateKey
    and updates on AppState 'active' when the calendar day changed —
    the reusable primitive for anything that must not freeze "today"
    at mount.
    Serves issues 7, 22.

F6. Errors stop pretending to be success
    a) useAsyncLoad (lib/hooks/, new): wraps a context's load with
       status 'loading' | 'ready' | 'error' + retry(). An error is a
       distinct state — never defaults-presented-as-truth. Also ignores
       a stale run whose deps changed mid-flight (cancelled flag +
       isStale() passed to the loader): Settings/Nutrition/Workout
       share one copy-pasted load effect with NO such guard today, so
       an in-flight load for the old user can clobber the new one —
       retires that skeleton and the race across all three at once.
    b) AppLoadingScreen error variant (no new component): when a load
       has failed, the existing loading screen fades in "Having
       trouble loading your data — Tap to retry" wired to the
       retryLoad(s); reverts to the plain spinner while retrying.
    c) reportPersistFailure(scope, error, { reload }) (lib/powersync/
       persistErrors.ts, new): Sentry capture + a throttled user
       alert + rollback-by-reload (re-run the owning context's load
       from SQLite so the UI shows disk truth — one universal
       rollback instead of per-handler inverse operations).
    Serves issues 6, 17 (and the spirit of 2 and 20).


CRITICAL (data loss, security, broken core flows)
-------------------------------------------------

*2. Anyone who ever contacted support can never delete their account
   The server delete function forgets the support_requests table. The
   database refuses to remove a user who still has rows there, so
   deletion fails forever. Worse, the six deletes that ran first are not
   error-checked, so the user's data is wiped even though the account
   survives.
   Where: lib/supabase/functions/deleteAccount/index.ts
   Fix: also delete support_requests, check every delete's error, do it
   all in one transaction.

   PLAN
   Root cause: deletion is a hand-maintained list of table deletes in
   application code. Any new user-owned table (support_requests today,
   whatever comes next tomorrow) silently breaks it, and per-table
   error checking is busywork that was (predictably) skipped.
   Steps:
   1) Push ownership into the schema: migration that re-declares every
      top-level user_id foreign key as ON DELETE CASCADE — workouts,
      user_exercises, nutrition_entries, saved_nutrition_entries,
      weight_progress, settings, support_requests. (Child tables
      already cascade from their parents.) Version it as
      lib/supabase/migrations/user_cascade.sql.
   2) Shrink the edge function to: authenticate →
      auth.admin.deleteUser(userId) → check the ONE error → respond.
      Postgres deletes all user rows atomically in the same
      transaction as the auth user — nothing partial, nothing to
      forget, no per-table error handling to maintain.
   3) Rule going forward (one line in the migration header): any new
      table referencing auth.users must declare ON DELETE CASCADE —
      deletion coverage is then automatic forever.
   Files: new migration, lib/supabase/functions/deleteAccount/index.ts.
   Verify: seed a user with data in every table incl. a support
   request → delete → auth user and all rows gone in one shot; make
   deleteUser fail → nothing was deleted (atomicity).

4. The paid AI and food-search features are free on the server
   The two server functions only check that you're signed in - never
   that you're subscribed, and there's no rate limit. Any free account's
   token can call the AI analysis endpoint directly and run up the
   OpenAI bill.
   Where: lib/supabase/functions/fetchOpenAI + fetchFoodDB
   Fix: check the subscription on the server (RevenueCat lookup) and add
   per-user rate limits.

   PLAN
   Root cause: authorization is conflated with authentication —
   entitlement exists only as client-side UI state (hasPremium hides
   buttons), so the server grants the paid capability to any valid
   JWT.
   Steps:
   1) One shared guard, used by both functions as their first line
      after JWT validation:
      lib/supabase/functions/_shared/entitlement.ts exporting
      requirePremium(userId) — RevenueCat REST subscriber lookup
      (secret key in an env var; app_user_id is the Supabase user id,
      which BillingContext already uses for Purchases.logIn), require
      an active 'LiftTrition Pro' entitlement, else return a 403
      Response. Cache per-user results in memory ~5 min so hot users
      don't cost a RevenueCat call per request.
   2) Per-user daily quota in the same guard: api_usage(user_id, day,
      calls) table + one atomic-increment RPC; over the cap (e.g.
      vision N/day, search M/day, from env) → 429. DB-backed so it
      survives edge-function instances, and doubles as usage
      analytics.
   3) Defense in depth on the client: cameraScreen and foodDBModal
      check hasPremium on mount and redirect to the paywall (closes
      the deep-link bypass past the FAB gate). Export the
      entitlement id as a constant from BillingContext (shared with
      issue 20) instead of the current string literal.
   Files: _shared/entitlement.ts (new), fetchOpenAI/index.ts,
   fetchFoodDB/index.ts, api_usage migration, cameraScreen.tsx,
   foodDBModal.tsx, context/BillingContext.
   Verify: curl the endpoint with a free account's JWT → 403; with a
   premium JWT → works; exceed the daily cap → 429; free user
   deep-linking to the camera lands on the paywall.

*5. One mis-tap in the archive screen permanently deletes a workout
   The trash icon there deletes the workout AND all its logged history
   instantly - no "are you sure?", no undo - and it sits right next to
   the restore button. Everywhere else in the app deletion asks first.
   Where: app/workoutScreens/archiveModal.tsx
   Fix: use the same confirmation alert as the main screens.

   PLAN
   Root cause: there is no shared "confirm a destructive action"
   primitive — every screen hand-rolls its Alert, so a screen that
   forgets simply has no confirmation (the audit's minor list shows
   the policy already drifting site by site).
   Steps:
   1) Add confirmDelete({ title, message, onConfirm }) in
      lib/utils/confirmDelete.ts — the standard two-button
      Cancel / Delete(destructive) Alert, ~10 lines.
   2) archiveModal trash buttons call it with the same warning copy
      the main screen uses ("Deleting a workout will delete all logs
      within the workout…"), for both workouts and exercises.
   3) Adopt the helper at the other delete sites (workoutScreen /
      exerciseScreen option alerts, saved-meal unsave) as they get
      touched — from now on destructive-confirm UX has one owner,
      so it cannot diverge again.
   Files: lib/utils/confirmDelete.ts (new), archiveModal.tsx.
   Verify: tap trash on an archived workout → confirmation names the
   log loss; Cancel keeps everything; Delete removes it.

MAJOR (wrong behavior, bad UX)

8. Weighing in secretly rewrites your goals
   Every body-weight update re-decides lose/maintain/gain by comparing
   against the goal weight exactly. A "maintain" user who logs 0.5 lb
   over is silently switched to "lose" with a 250-cal deficit; dip under
   and they become "gain". It also resets the pace and overwrites any
   hand-tuned macros. Same silent macro rewrite on height/activity edits.
   Where: context/SettingsContext/functions/bodyWeightFunctions.tsx
   Fix: don't flip the goal type without asking; don't clobber custom
   macros (add a customized flag).

   PLAN
   Root cause: the weigh-in path conflates two responsibilities that
   need opposite policies. TARGETS (calorie/macro numbers) should
   track the user's weight — that's advertised in the modal copy and
   users expect it. INTENT (goalType, pace) belongs to the user — but
   the code re-derives it with an exact weight-vs-goal comparison, so
   normal daily scale noise flips maintain users into ±250 kcal
   swings, a cutter who dips past goal silently becomes a bulker, a
   flip resets pace to 0.5, and every weigh-in regenerates all four
   macro goals, wiping hand-tuned values — because nothing records
   that they were hand-tuned.
   Market check (researched 2026-07): Cal AI updates nothing on a
   weigh-in (targets are static after onboarding — criticized as TOO
   manual); MacroFactor, the most automated tracker, adjusts target
   numbers weekly from logged data but the goal direction is always
   user-chosen. No shipping tracker silently flips direction.
   The rule to adopt: TARGETS ARE DERIVED, INTENT IS OWNED.
   Automation may update numbers within the user's chosen goal, and
   may END a phase into maintenance (announced), but only the user
   starts a cut or a bulk.
   Steps:
   1) computeBwUpdate keeps updating bodyWeight AND regenerating
      targets for the CURRENT goalType (numbers keep tracking
      weight, as today) — but never touches goalType or goalPace.
      Delete the exact-comparison flip and the 0.5 pace reset.
   2) macrosCustomized flag (new settings column: Postgres
      migration, AppSchema, Settings type, settingsToRow/
      rowToSettings): set true when the user hand-edits macros
      (EditMacroGoalModal / manual adjustNutrition path); cleared
      whenever targets are explicitly regenerated (wizard
      completion, or accepting any "Recalculate?" prompt). Every
      IMPLICIT recalculation — weigh-ins, height/activity edits —
      is skipped while the flag is true, so hand-tuned targets
      survive the app's most frequent action.
   3) Goal-crossing moment: when a weigh-in crosses goalWeight in
      the goal's direction (previous weight on one side, new weight
      at/past it — derived from prev vs new, no stored state), show
      a one-time congrats prompt: "Goal reached! Update my plan"
      (routes into the adjustNutrition wizard) / "Not now".
   4) Auto-maintain safety net (answers "what if they never tap?"):
      if goalType is lose/gain and the logged weight sits PAST
      goalWeight by a deadband (unit-aware constant, ~2 lb / 1 kg —
      big enough that boundary noise can't trigger it), switch
      goalType to 'maintain', regenerate targets for maintenance
      (still respecting macrosCustomized), and announce it: "You've
      passed your goal — we've switched you to maintenance. Set a
      new goal anytime." One-way by design: automation only ever
      moves a user TO maintenance — a stale plan degrades to the
      safest state (holding at goal) instead of an unwanted surplus
      or deficit.
   5) Persistent banner instead of a missable alert: while goalType
      is lose/gain and weight is at/past goalWeight, the nutrition
      screen shows "Goal reached — set your next goal" (reuse the
      ActivityBanner pattern) linking to the wizard. Pure derived
      render-time state — cannot be lost or forgotten.
   6) Height/activity edits follow the same one rule: auto-recalc
      numbers for non-customized users (consistent with weigh-ins),
      never touch goalType; customized users get an explicit
      "Recalculate targets?" prompt instead of silence.
   7) Copy: updateBWModal subtitle stays honest per state — targets
      update automatically (default) / your custom targets are kept
      (customized).
   Files: bodyWeightFunctions.tsx, SettingsContext/index.tsx +
   database/powersyncStore.ts, settings migration
   (macros_customized), lib/powersync/AppSchema.ts,
   updateBWModal.tsx, profile.tsx, adjustTraining.tsx,
   EditMacroGoalModal.tsx, goal-reached banner component (new).
   Verify: maintain user logs +0.5 lb → goalType/pace untouched, no
   kcal seesaw; lose user's calorie target tracks weight down across
   weigh-ins; hand-edit protein → later weigh-ins keep it; crossing
   goal → congrats prompt once + banner; ignoring everything and
   passing goal by 2+ lb → announced auto-switch to maintenance;
   automation never starts a surplus or deficit on its own.

11. Half a serving becomes a full serving
    The servings box uses parseInt, so "0.5" turns into 1 - double what
    the user actually ate, with no warning. (The photo editor supports
    decimals, so the flows disagree.)
    Where: foodDBModal.tsx + savedNutritionModal.tsx (confirmAddItem)
    Fix: parseFloat + validate > 0.

    PLAN
    Root cause: same class as issue 10 — servings are parsed with a
    different, integer-only grammar in these two modals while the
    photo editor accepts decimals. One concept, two grammars.
    Steps:
    1) Both confirmAddItem handlers parse with parseNumericInput
       (F1) and accept only parsed > 0 — "0.5" is a valid half
       serving; 0, negative, or unparseable input leaves the Add
       button disabled (no silent fallback to 1).
    2) Set the quantity TextInputs to keyboardType="decimal-pad" so
       the keypad offers the separator.
    3) Totals stay clean automatically: entry math already
       multiplies by quantity, and the issue-3 boundary sanitizes
       the final calories (column now REAL), so fractional servings
       can't reintroduce the sync wedge.
    Files: foodDBModal.tsx, savedNutritionModal.tsx.
    Verify: log 0.5 servings from food search → half the macros are
    recorded; typing "0" or garbage can't confirm; whole numbers
    behave exactly as before.

13. Swiping away the "Analyzing..." screen doesn't cancel anything
    The AI call keeps running. Up to 30s later it adds the meal anyway
    and force-closes whatever screen the user has open since; on failure
    it pops a "Try Again" alert over some unrelated screen. Re-taking
    the photo after "cancelling" = duplicate meals and duplicate paid
    AI calls.
    Where: app/nutritionScreens/analyzingModal.tsx
    Fix: block the swipe-dismiss on that screen, or track cancelled
    state and drop the result.

    PLAN
    Root cause: a 30-second paid, uncancellable operation lives in a
    casually dismissible screen, and its continuation assumes the
    screen still owns navigation (router.dismissAll() fires wherever
    the user has wandered to).
    Steps:
    1) Make the commitment explicit — the route is not dismissible
       while analyzing: analyzingModal's Stack.Screen gets
       gestureEnabled: false (it currently inherits modal
       swipe-to-dismiss from modalPresentation), and Android
       hardware back is blocked for the screen (usePreventRemove).
       The user is committed for at most 30s (the existing timeout)
       with visible progress; the failure alert still offers Try
       Again / Cancel.
    2) Guard the continuation anyway (cheap insurance for any future
       programmatic dismissal): a doneRef/unmounted ref checked after
       the await — if the screen is gone, drop the result: no
       addNutrition, no dismissAll, no orphan Alert.
    Result: "cancel then re-take" duplicates become impossible
    because there is no half-cancelled state — analysis either
    completes on-screen or fails on-screen.
    Files: app/_layout.tsx (route options), analyzingModal.tsx.
    Verify: swipe during analysis → screen stays; success dismisses
    to home exactly once; simulate failure → alert appears on the
    analyzing screen itself; no path produces two entries or two
    paid calls.

14. Nearly every "Add" button can be double-tapped
    Add meal, Add All (food DB + saved meals), Add Exercises, Add
    Workout, and Use Photo all stay live during the closing animation -
    a quick double-tap creates duplicates, and Use Photo runs TWO paid
    AI analyses. (Purchase buttons and set-logging are guarded
    correctly.)
    Where: the listed modals' submit handlers
    Fix: set a submitted flag / disable the button on first press.

    PLAN
    Root cause: there is no shared single-flight primitive, so every
    CTA re-implements (or forgets) the in-flight flag, and the modal
    close animation leaves buttons live for a frame or two. The two
    guarded flows (purchases, logsModal) prove the pattern — it just
    isn't reusable.
    Steps:
    1) Build useSubmitOnce (F2): a synchronous ref-based guard (state
       updates are a frame too late for a real double-tap) plus a
       `submitting` boolean for the disabled style.
    2) Wrap the offenders: addNutritionModal "Add meal", foodDBModal
       "Add All", savedNutritionModal "Add All", addExerciseModal
       "Add N Exercises", addWorkoutModal create, cameraScreen
       "Use Photo" AND the shutter (takePicture has the same gap).
       Handlers that end in router.back()/push never reset (the
       screen is leaving); retryable ones reset in finally.
    3) House rule going forward: any CTA whose handler awaits or
       navigates uses useSubmitOnce — one import, no bespoke flags.
    Files: lib/hooks/useSubmitOnce.ts (new), the six screens above.
    Verify: machine-gun-tap every listed CTA → exactly one entry /
    workout / analysis; buttons visibly disable during the closing
    animation; Use Photo can never bill twice.

15. Denying camera access once bricks the AI scan feature

    does nothing (iOS won't re-prompt). No link to Settings is offered.
    Where: app/nutritionScreens/cameraScreen.tsx
    Fix: when iOS says it can't ask again, open the Settings app.

       call comes back canAskAgain:false, swap the button
       immediately — no dead tap.
    3) pickFromLibrary's denial alert gains an "Open Settings"
       action via the same helper.

    Scope expanded — unified scan screen (full spec:
    docs/superpowers/specs/2026-07-14-unified-camera-scan-screen-
    design.md). The permission fix above is the seed of a single
    cameraScreen that handles all four states (free vs premium ×

    bounce are solved in one place.
    Second problem: the camera FAB (app/(tabs)/index.tsx:62)
    hard-bounces non-premium users straight to the subscription
    page — they never see what they're paying for.
    Design: one static "ScanBackdrop" (scan chrome over a

    without granted permission) with a swappable "ScanPromptCard"
    overlay. Free → "Upgrade to scan" (→ subscription); premium &
    !granted & canAskAgain → "Grant Permission"; premium & !granted
    & !canAskAgain → "Open Settings"; premium & granted → live
    CameraView (unchanged). Free path never requests permission.
    The premium priming screen stays (one-shot iOS prompt — priming
    lifts the Allow rate); no cold auto-prompt.
    Extra steps:
    4) New presentational units: ScanBackdrop.tsx and
       ScanPromptCard.tsx (components/NutritionComponents/).
    5) cameraScreen.tsx becomes a hasPremium × permission state
       router composing those pieces; live camera / preview /
       takePicture / mode+flash state unchanged.
    6) index.tsx camera FAB always opens cameraScreen — drop the
       hasPremium branch and nutritionUnavailableFabButtons on the
       camera button only (Food DB button out of scope).
    Phasing: Phase 0 builds ScanBackdrop + ScanPromptCard + a Dev
    Hub preview page (all prompt variants, light/dark) to lock the
    look with zero risk; Phase 1 wires the helper (TDD), the router,
    and the FAB into the real flow.
    Files: lib/utils/permissions.ts (new), cameraScreen.tsx,
    app/(tabs)/index.tsx, ScanBackdrop.tsx (new),
    ScanPromptCard.tsx (new), + Dev Hub harness (Phase 0).
    Verify: Dev Hub → Scan Screen shows every prompt variant over

    Upgrade → subscription; upgrade → return → permission/live
    path. Premium first run → priming → prompt → camera. Permanent
    deny → "Open Settings" deep-links to the app's settings page;
    same for the library picker.

16. You cannot sign out while offline
    Sign-out requires a connected sync first; offline it fails with
    "PowerSync is not connected." and only an OK button. The force
    sign-out fallback is only offered for timeouts, not for this error.
    Where: profile.tsx error handling + FlushUploads.ts
    Fix: offer force sign-out (with the data-loss warning) here too.

    PLAN
    Root cause: the escape hatch is keyed to one error subclass
    (UploadFlushTimeoutError) when the meaningful category is "the
    flush cannot complete" — not-connected and disconnected-mid-flush
    fall through to a dead-end OK alert.
    Steps:
    1) F4: UploadFlushTimeoutError and UploadFlushNotConnectedError
       extend a common UploadFlushError base; export
       isUploadFlushError(). Any future flush-failure type inherits
       the escape hatch automatically instead of re-opening this bug.
    2) profile.tsx handleSignOut: branch on isUploadFlushError →
       the existing force-sign-out alert, with the message adapted
       to the case ("You're offline — sign out anyway? Unsynced data
       will be lost." vs the current "still uploading…" text).
    3) Make the forced path actually work offline: forceSignOut ends
       in clearLocalSession() (F4), which uses
       supabase.auth.signOut({ scope: 'local' }) and guards each
       teardown step — no network dependency, no half-teardown.
    Files: FlushUploads.ts, accountFunctions.tsx, profile.tsx.
    Verify: airplane mode → Sign Out → data-loss warning → Force
    sign out → login screen; relaunch (still offline) stays signed
    out.

18. Creating the same custom exercise on two devices jams sync
    The server requires unique exercise names per user, but the upload
    code has no handling for that conflict (unlike settings/weight).
    One duplicate = the same forever-retry sync jam as issue 3.
    Where: lib/powersync/Connector.ts (createRecord)
    Fix: check-then-update branch for user_exercises like settings has.

    PLAN
    Root cause: unique-constraint handling is copy-pasted per table,
    so each new constrained table starts broken until someone
    remembers the pattern (CLAUDE.md gotcha 3 documents the rule;
    the code doesn't enforce it).
    Steps (F3):
    1) Replace the two hand-written branches with a declarative
       registry + one generic path: UNIQUE_KEYS = { settings:
       ['user_id'], weight_progress: ['user_id','date'],
       user_exercises: ['user_id','name'] }. createRecord looks up
       the table's keys; if registered and present on the record,
       select the existing server row by those keys → UPDATE with
       the local id stripped (keeping the server row's id, exactly
       like the settings branch does today) → else INSERT. ~25
       lines replace ~60, and the next constrained table is a
       one-line registration.
    2) The issue-3 backstop (skip + report non-retryable 23505s)
       stays underneath as the net for anything the registry misses
       — a conflict can cost one report, never a wedged queue.
    Files: lib/powersync/Connector.ts.
    Verify: create the same custom exercise name from two devices
    (or re-create before a delete syncs) → second upload updates the
    existing row; upload queue drains; Connector unit tests cover
    all three registered tables.

20. "Restore Purchases" says it worked even when there's nothing
    For a user who never subscribed, restore still pops "Purchases
    restored successfully!" while everything stays locked. It also has
    no busy state, so it can be double-fired or run during a purchase.
    Where: subscription.tsx + paywall.tsx (handleRestore)
    Fix: check what actually came back; add a restoring flag.

    PLAN
    Root cause: the screens treat "the restore call resolved" as
    "something was restored" — RevenueCat resolves successfully with
    zero entitlements — and the restore outcome/in-flight state
    isn't modeled anywhere, so each screen improvised (one lies,
    one completes onboarding unconditionally).
    Steps:
    1) BillingContext owns the outcome: restorePurchases returns the
       fresh CustomerInfo; add a `restoring` state alongside the
       existing customerInfo update; export ENTITLEMENT_ID
       ('LiftTrition Pro'), deduping the literal hasPremium uses
       (shared with issue 4's server check).
